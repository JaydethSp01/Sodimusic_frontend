# Rendimiento — aplicación de §5 del diseño v3 (2026-10-17)

Alcance: caché de datos públicos (`fetchPublic` + `revalidateTag`), fuentes, `next.config.mjs` (imágenes y cabeceras) y medición. Los componentes cliente no se tocaron: las recomendaciones por archivo están en §6 para aplicarlas después.

## 1. Cambios aplicados

### 1.1 Caché de datos públicos (`lib/api.ts`)

- `fetchPublic` infiere por ruta una **política de caché por recurso**: `revalidate` 60 s por defecto; **300 s** para `/api/site-config` y `/api/channels` (también `/api/youtube-channels` por si el backend usa ese nombre). El `init.next.revalidate` explícito del llamador siempre gana (las páginas que pasan 30/120 siguen igual).
- Cada fetch lleva el `tag` de su recurso (`site-config`, `channels`, `beats`, `products`, `releases`, `productions`) unido a los tags que pase el llamador. Helper exportado: `publicTags` (+ `resolvePublicCachePolicy`, `PUBLIC_REVALIDATE_DEFAULT`, `PUBLIC_REVALIDATE_SLOW`).
- Se mantiene el comportamiento de error: ante fallo de red devuelve `Response` 503 en vez de lanzar.
- `lib/site-config-server.ts` usa `publicTags.siteConfig` y 300 s.

### 1.2 Invalidación desde el admin (`app/actions/*`)

Edición mínima en cada acción (crear/editar/borrar): `revalidateTag(publicTags.<recurso>)` antes de los `revalidatePath` existentes.

| Acción | Tag | Paths añadidos |
|---|---|---|
| `admin-products-actions.ts` (`revalidateShop`) | `products` | `/tienda/[slug]` (page) |
| `admin-beats-actions.ts` | `beats` | — (ya tenía `/beats`) |
| `admin-releases-actions.ts` | `releases` | `/` (los releases destacados salen en home) |
| `admin-productions-actions.ts` | `productions` | — (ya tenía `/productions` y `/`) |
| `site-config-actions.ts` (`publishSiteAction`) | `site-config` + `channels` | `revalidatePath("/", "layout")` (navbar/footer de todo el sitio público) |

No se tocaron `booking-actions.ts` ni `newsletter-actions.ts`.

### 1.3 Fuentes (`app/layout.tsx`)

- `display: "swap"` en las tres (ya estaba).
- Pesos: Bebas Neue y Syne Mono solo existen en 400. DM Sans pasa de eje variable `100 1000` a `["400","500","600"]`, los únicos usados (`font-normal` ×4, `font-medium` ×52, `font-semibold` ×20; no hay `font-bold`/`light` en el código). **Nota**: Google sirve el mismo fichero variable (37 kB, hash `13971731025ec697`) para ambos casos, así que el ahorro de bytes es 0; la ganancia real es la siguiente.
- `preload` solo de la display principal (Bebas Neue, 8.6 kB). Antes se precargaban 3 ficheros (56 kB) en el camino crítico; ahora 1 (8.6 kB). DM Sans y Syne Mono se descargan al primer uso, con `swap` + fallback ajustado por `next/font`.

### 1.4 `next.config.mjs`

- `images.formats: ["image/avif","image/webp"]`, `deviceSizes: [360,414,640,768,1024,1280,1536,1920]`, `imageSizes: [48,64,96,128,160,256,384]`, `minimumCacheTTL: 86400`. `remotePatterns` existentes intactos (unsplash, ytimg, youtube, scdn, blob de Vercel, uploads del backend).
- `poweredByHeader: false`.
- Cabeceras en `/:path*`: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` que bloquea `camera`, `microphone`, `geolocation`, `payment`, `usb` y deja `fullscreen` para `self` + `youtube.com`/`youtube-nocookie.com` y `picture-in-picture=*`. Sin CSP ni `X-Frame-Options` para no romper embeds ni admin. Comprobado: el único API sensible usado es `navigator.clipboard.writeText` (QR studio), no afectado; el iframe de YouTube pide `accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture`, todos con política por defecto o permitidos.
- `Cache-Control: public, max-age=86400, stale-while-revalidate=604800` para estáticos de `/public` (`ico|png|jpg|jpeg|webp|avif|svg|woff2`). `/_next/static` ya es inmutable por defecto en Next, no se duplica.

### 1.5 Scripts de medición (`scripts/perf/`)

- `scripts/perf/lighthouse.mjs --base <url> --out <dir> [--routes /,/beats,/tienda,/canales]`: Lighthouse 12 móvil (rendimiento + accesibilidad), imprime tabla Markdown y guarda JSON. Usa `CHROME_PATH` o `/usr/bin/google-chrome`.
- `scripts/perf/vitals.mjs --base <url> [--routes ...] [--runs N]`: fallback con Playwright (Pixel 5, red ~Slow 4G, CPU ×4) que mide TTFB, LCP, CLS y bytes por tipo vía `PerformanceObserver` + CDP.

Build local: `NODE_OPTIONS=--dns-result-order=ipv4first npm run build` (DNS local). Nota: `fetch` de node a `fonts.googleapis.com` falló por timeout de forma transitoria una vez; reintentar basta.

### 2.1 Dónde se va el LCP de `/` (4.1 s)

Fases del elemento LCP (`<img>` del hero, `fetchpriority="high"`): TTFB 1 322 ms → load delay 961 ms → load time 1 716 ms → render 53 ms.

### 6.1 Prioridad alta (afecta a todas las rutas públicas)

1. **`components/shared/navbar.tsx`** — único motivo por el que `framer-motion` (119 kB raw / 41 kB transfer) entra en la capa `/(public)/layout`. Usa `motion.div`/`motion.li` + `AnimatePresence` solo para el menú móvil en un portal.
   - Opción A (recomendada): quitar framer del navbar. Animar el panel con clases Tailwind (`transition-[opacity,transform]`, `data-[state=open]`) o `tailwindcss-animate` (ya instalado); el stagger de los `<li>` con `animation-delay` por índice. Cero JS extra.
   - Opción B: extraer el panel a `components/shared/navbar-mobile-menu.tsx` y cargarlo con `dynamic(() => import(...), { ssr: false })` al primer `onClick` del botón hamburguesa. framer deja de estar en First Load; se descarga al abrir el menú.
   - Y en cualquier caso usar `LazyMotion` + `m` + `domAnimation` (≈ 15 kB en lugar de 40 kB transfer) en los componentes que sigan necesitando framer.
2. **`features/shop/components/cart-drawer.tsx`** (montado en `app/(public)/layout.tsx`) — arrastra `@radix-ui/react-dialog` + `react-remove-scroll` (41 kB raw) en toda ruta pública aunque el carrito esté vacío. Convertir a `dynamic(() => import("./cart-drawer"), { ssr: false })` desde un wrapper cliente pequeño que lo monte solo cuando `useCartStore` tenga ítems o el usuario pulse el botón del carrito. `cart-button.tsx` (zustand, 4 kB) puede quedarse estático.
3. **`components/providers.tsx`** — `<Toaster>` de sonner (33 kB raw) en la raíz: solo lo usan el admin, `beats-store`, `booking-wizard` y `add-to-cart`. Mover el `<Toaster>` a `app/admin/layout.tsx` y, en lo público, a un `dynamic(() => import("sonner").then(m => m.Toaster), { ssr: false })` montado dentro de `app/(public)/layout.tsx`. `SessionProvider` de next-auth (10 kB) también debería vivir solo en `app/admin/**`: en lo público ningún componente cliente usa `useSession` (`site-preview-banner` es server y usa `auth()`).

### 6.2 Home (`/`)

4. **`components/landing/home-page-motion.tsx`** (`HomeFadeSection`, `HomeStagger`, `HomeStaggerItem`, `HomeFigureMotion`) — wrappers `whileInView` de fade/stagger que envuelven secciones enteras y obligan a que `home-shop-section.tsx` y `youtube-channels-section.tsx` (server components) rendericen hijos dentro de límites cliente. Mantener `priority`, `quality={70}`, `sizes="100vw"`. Quita framer del camino del LCP.

## 7. Resultado bundle (aplicación de §6, 2026-10-17)

Se aplicaron los puntos 1–10 y 12 de §6 (quedan 11 y 13, ver 7.4). Build local `NODE_OPTIONS=--dns-result-order=ipv4first npm run build`, misma máquina; "antes" es el árbol de trabajo justo antes de estos cambios (copia limpia construida aparte para poder medir la unión de chunks).

**Cómo leer las cifras.** La columna *First Load JS* de la tabla de `next build` suma los chunks compartidos (react-dom + runtime, 87.6 kB) y los de la **página**, pero **no los chunks propios de los layouts** (`/layout`, `/(public)/layout`): por eso `/legal/*` marcaba 96.6 kB cuando el navegador bajaba 190 kB (framer-motion del navbar, sonner y next-auth vivían en los layouts). La columna *real* es la unión de los JS de `/layout` + `/(public)/layout` + la página según `.next/app-build-manifest.json`, en kB gzip (`node scripts/perf/first-load.mjs`, nuevo en §1.5), que es lo que realmente descarga el navegador en la primera carga.

### 7.2 Qué cambió (archivos)

- **Nuevos**: `components/shared/reveal.tsx` (cliente: `IntersectionObserver` + `data-reveal`, `amount 0.1`, `once`; anima con la Web Animations API, `element.animate`, con las mismas curvas/duraciones de `lib/animations.ts`), `components/shared/reveal-item.tsx` (ítem escalonado sin JS + `RevealNoScriptFallback`), `components/shared/lazy-toaster.tsx`, `components/admin-providers.tsx`, `features/shop/components/cart-drawer-lazy.tsx`, `features/booking/components/booking-wizard-lazy.tsx` (esqueleto + `dynamic`), `scripts/perf/first-load.mjs`.
- **Sin framer-motion y ahora server components**: `hero-section.tsx` (entrada CSS `.hero-enter`, mantiene `priority`, `quality={70}`, `sizes="100vw"`), `genres-grid.tsx` (hover con `motion-safe:hover:-translate-y-1`), `home-story-timeline.tsx`, `home-services-section.tsx`, `artists-crew-grid.tsx`, `production-card.tsx`, `home-page-motion.tsx` (mismos nombres exportados sobre `Reveal`/`RevealItem`; `home-shop-section`, `youtube-channels-section`, `channels-grid` y `/tienda` no cambian).
- **Cliente sin framer**: `navbar.tsx` (panel móvil con `tailwindcss-animate`: `fade-in`/`fade-out` 280 ms + stagger de `<li>` por `animation-delay`; conserva portal, `aria-expanded`, Esc, bloqueo de scroll y el desmontaje tras la salida), `stats-section.tsx` (`IntersectionObserver` 0.3 + `matchMedia`).
- **CSS** (`app/globals.css`): keyframe `heroEnter` + `.hero-enter` (hero), estado oculto inicial `[data-reveal]`/`[data-reveal-item]` (coincide con el HTML del servidor) y `prefers-reduced-motion` → todo visible sin animar. El reveal en sí se anima por JS (WAAPI, `fill: "backwards"`): al terminar no queda ningún estilo (los `hover:-translate-y-*` siguen funcionando) y **no se repite si un ancestro cambia de `display`** — con `@keyframes` CSS la línea de tiempo de escritorio (`hidden lg:block`) volvía a animarse al cruzar el breakpoint `lg` y en las capturas full-page de Chromium; se detectó en la comparación de capturas y por eso la primera versión con keyframes se sustituyó.
- **Carga diferida**: `providers.tsx` ya solo monta `GlobalUX`; `app/admin/dashboard/layout.tsx` envuelve con `AdminProviders` (`SessionProvider` + `Toaster`); `AddToCart`, `BeatsStore` y `BookingWizard` montan `LazyToaster`; `beats-store.tsx` carga `BeatInterestModal` con `dynamic` al elegir licencia; `app/(public)/booking/page.tsx` usa `BookingWizardLazy`; `app/(public)/layout.tsx` usa `CartDrawerLazy` y monta `RevealNoScriptFallback` una vez para todo lo público (antes solo en el home).
- `booking-wizard.tsx` y `booking-success-view.tsx`: `motion` → `m` + `LazyMotion features={domAnimation}` (chunks más pequeños; el del wizard además es async). `admin-dashboard-insights.tsx`: contador rAF propio en vez de `react-countup`. `package.json`: sin `react-countup`.
